# P01A, bloque 3: selección múltiple y publicación íntegra

## Implementado

El selector nativo de fotos permite hasta 20 imágenes, muestra orden de selección y conserva todos los assets. Archivos también permite selección múltiple. Cámara sigue individual. Se mantienen MIME, nombres, representación compatible y calidad del selector. Si devuelve más elementos que el límite, se informa el rechazo; nunca se descartan silenciosamente.

El móvil envía un manifiesto versionado con UUID y todas las partes en orden. Conserva la selección fallida y permite reintentar el mismo lote, cancelarlo o descartarla. El daemon recibe en una carpeta privada temporal, limita cantidad y 100 MiB totales, valida tamaños declarados y calcula SHA256 por archivo. Admite checksum de origen opcional, aunque el móvil todavía no lo calcula. Prefija el orden para conservar archivos con nombres iguales.

Publica el directorio completo mediante rename una vez que se verificaron todas las partes. Solo entonces prepara el portapapeles. Un lote incompleto, corrupto o con partes inesperadas no modifica el portapapeles ni deja archivos parciales visibles. Nunca inyecta Ctrl+V ni Enter durante la subida. La UI ofrece pegar explícitamente después del recibo.

El recibo se guarda con el lote. Reintentar el mismo ID y manifiesto devuelve ese recibo, incluso después de reiniciar el daemon. No vuelve a guardar ni reemplaza una copia más reciente del usuario. Un manifiesto distinto con el mismo ID se rechaza. La UI no ofrece pegado automático a partir de un recibo recuperado, porque no demuestra propiedad actual del portapapeles.

Las imágenes múltiples se publican como archivos independientes mediante una lista URI ordenada, con formatos GTK/GNOME/KDE. No se fabrica un collage. La imagen individual mantiene la ruta PNG existente para consumidores de imágenes.

## Pruebas

- Go: publicación completa, orden, nombres duplicados, checksum por archivo, idempotencia y recuperación tras reiniciar el servidor; rechazo y limpieza por parte faltante, tamaño/checksum incorrecto, campo extra o nombre inseguro.
- Móvil: selección completa de fotos/documentos, límite explícito, manifiesto antes de archivos, validación de identidad/cantidad/tamaño del recibo, reintento del mismo ID, conservación del lote y una sola acción de pegado. Once suites pasan y TypeScript pasa.
- GTK real aislado: lista íntegra en `text/uri-list`, `x-special/gnome-copied-files` y `application/x-kde4-urilist`; lectura después de 1250 ms y solicitudes repetidas. Al crear una copia sintética nueva, el proveedor anterior se retira. Evidencia en `outputs/p01a-03/clipboard-result.json`, log y recursos.
- La primera variante puramente Wayland del proveedor GTK no ofreció formatos al consumidor. Se verificó el camino XWayland privado que ya utiliza el proveedor en escritorios con DISPLAY. No se tocó clipboard personal. El fallback Wayland sin XWayland y consumidores de aplicaciones específicas siguen pendientes.

## Límites y continuación

P01A.8–.10 avanzan, no se declaran cerradas. Falta reanudar solo partes incompletas: el reintento actual evita duplicar lotes completos, pero vuelve a subir un lote incompleto. Faltan checksum de origen en el móvil, límites negociados, selección revisable por archivo antes de subir, limpieza de staging huérfano tras crash y prueba de iCloud/HEIC/memoria en teléfonos. GET del recibo está disponible; la recuperación móvil actual reutiliza POST con el mismo manifiesto.

La prueba GTK verifica formatos y bytes, no garantiza que cada web/app admita pegar varios archivos. El destino habitual del usuario, navegador y administrador de archivos deben probarse con el candidato. Un host antiguo rechaza el endpoint nuevo con indicación de actualizar; no se reduce una selección múltiple a una sola imagen.

El bloque también conserva atajos explícitos con modificador en el modo de texto literal. La semántica por layout y los recibos de acciones siguen pendientes de P01A.3/.7.

No desplegado. El usuario pidió cerrar el trabajo actual por cuota; dejar este checkpoint pausado hasta que solicite continuar. El candidato requiere nuevo build nativo desde P01A-02. Rollback mediante revert en el checkout aislado. Los lotes guardados quedan en Downloads/Phonepad y no se borran al revertir.
