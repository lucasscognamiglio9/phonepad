# P01: calidad estable y feedback verificable

## Entregado

P01.1–P01.5 implementadas. P01.6 tiene comparación de política y encoder real de host; quedan pendientes el detalle visual y la transmisión completa bajo perfiles de red en un receptor físico. No se desplegó este candidato.

El controlador conserva una ventana de RTT de 30 segundos por ruta. Al cambiar el par ICE, reanudar o recibir feedback tras más de cinco segundos, descarta referencias antiguas sin reiniciar el bitrate. El RTT mínimo queda disponible en la explicación de cada decisión. Una latencia estable o un buffer de presentación alto no causan por sí solos recortes repetidos.

La política observa pérdida moderada superior a 2,5% o crecimiento conjunto de RTT y buffer. Exige dos segundos de persistencia y reduce 15% como máximo cada tres segundos. Pérdida desde 8% reduce 25% como máximo cada segundo. Recupera hasta 25% por paso cada dos segundos con muestras sanas; conserva límites de 350 kbps y el máximo original del codec. Estos parámetros están validados en fixtures y necesitan la calibración de red/dispositivo de P01.6; no son GCC.

El receptor envía `null` cuando desconoce una métrica. No usa deltas entre SSRC/IDs distintos, contadores que retroceden, muestras repetidas o tiempos inválidos. Usa el par señalado por transport y solo admite el fallback nominated cuando hay un único candidato. La secuencia evita procesar dos veces feedback antiguo. La API Go conserva los campos y los `null` sin transformarlos.

Cada decisión registra entrada, motivo, duración del estado, referencia de RTT, secuencia y bitrate solicitado. La respuesta y log del servidor incluyen bitrate aplicado. El cliente consume las métricas de encode y expone el último resultado mediante `VideoSession.getDiagnostics()`, sin historial creciente ni cambios visuales. Se restauró además el import de math que seguía siendo necesario para el log nativo tras la extracción P00, con regresión de integración.

Estos FPS proceden de la grabación decodificada del host, no de presentación en el teléfono. Los ciclos no están alineados cuadro a cuadro; no se midió PSNR/SSIM ni detalle visual en iPhone. ## Verificación y rollback

Pasaron 29 pruebas Python, 6 del laboratorio, las 10 suites móviles, TypeScript y las pruebas Go del gateway RTC. Incluyen el viaje de métricas desconocidas, cambio de ruta y consumo de diagnósticos. Paquete servidor importable; comprobar hashes de `release.json` antes de usarlo.

Rollback de política en el servidor candidato: `PHONEPAD_RATE_POLICY=legacy`. Conserva observabilidad y guardas para valores desconocidos, pero reproduce las decisiones de los fixtures antiguos cuando las métricas están presentes. La selección se hace al crear una sesión, por lo que exige recrearla. La prueba `test_legacy_rollback_reproduces_fixture` comprueba esta compatibilidad. No se cambió la configuración del servicio activo.

Para repetir el A/B, ejecutar `tools/hfr/isolated.py` con `PHONEPAD_LAB_RATE_AB=1`, `PHONEPAD_LAB_SECONDS=20` y el runtime de P00 dentro de una unidad temporal systemd con ruta absoluta del script, `MemoryMax=1000M`, `RuntimeMaxSec=75` y `KillMode=control-group`. El laboratorio crea exactamente dos ciclos, legacy/windowed. Decodificar ambos con `verify_frames.py` como indica el README P00 y preservar las salidas antes de limpiar `/tmp`.

Referencias consultadas para esta fase: [Expo SDK 57](https://docs.expo.dev/versions/v57.0.0/) según AGENTS.md y [WebRTC Stats](https://www.w3.org/TR/webrtc-stats/) para selección de par, contadores y métricas acumuladas.
