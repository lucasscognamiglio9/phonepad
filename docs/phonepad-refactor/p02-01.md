## Implementación

- `mobile/src/lib/host-settings.ts` contiene el esquema persistido v1:
  `version`, `devices[]` con `id`, `name` y `origin`, y `selected`.
- La normalización admite únicamente orígenes HTTPS. Elimina la barra raíz al normalizar y rechaza credenciales, consultas, fragmentos y cualquier ruta adicional. No persiste tokens, contraseñas ni otros campos de autenticación.
- El límite local es de 16 equipos; nombres, identificadores, orígenes y el tamaño del documento tienen límites explícitos. No se fija ningún hostname personal.
- El proveedor nativo usa la API SDK 57 instalada de `expo-file-system` (`File` y `Paths.document`). Mantiene dos slots JSON propios con revisión, escribe el contenido completo en un archivo temporal del mismo directorio y reemplaza el slot más antiguo mediante `move(..., { overwrite: true })`. Como esa API puede borrar el destino antes de fallar, el slot válido restante permite recuperar la última revisión después de un reinicio; las escrituras se serializan y los fallos de lectura/escritura devuelven resultados recuperables. Una configuración desconocida no se sobreescribe automáticamente.
- `hostSettingsAdapter` y `loadSelectedHost()` son el punto de acceso exportado para inicializar el equipo seleccionado. El adaptador acepta un almacenamiento inyectado para pruebas y futuras separaciones de perfil.
- `mobile/src/screens/host-picker.tsx` ofrece una UI nativa simple para agregar, elegir y quitar equipos. La selección inicial se comunica mediante `onSelect(origin)`. El prop opcional `adapter` queda disponible para pruebas y reutilización posterior.
- `mobile/tests/host-settings.test.cjs` cubre validación HTTPS estricta (incluidas barras invertidas y direcciones sin esquema), fixture con dos equipos, guardado concurrente con rechazo de estado obsoleto, exclusión entre dos adaptadores sobre el mismo journal, eliminación del seleccionado sin autoselección, persistencia fallida y el recorrido temporal/reemplazo del proveedor Expo sin recompilar el proyecto. También comprueba que snapshots corruptos (incluido el archivo legado) o sobredimensionados no se tapan con un guardado posterior y que el límite de 64 KiB se verifica antes de leer.

## Integración y protección de contenido

El punto de entrada restaura el host seleccionado al abrir la app. Al volver con Equipos, muestra el selector sin reconectarse automáticamente. Cada origen monta una sesión propia; desmontar la anterior cierra socket, video, timers y coordinador de actualización. La elección se guarda antes de abrir el control. Quitar un host no abre otro equipo.

Control impide cambiar de host mientras quedan borradores, resultados inciertos o adjuntos pendientes y explica cómo resolverlos. El compositor informa cambios de estado pendiente mediante un booleano, sin elevar cada carácter al contenedor del video. Una actualización descargada también espera mientras hay contenido; terminar el borrador no dispara una recarga inmediata.

Las pruebas de `host-session`, `host-picker`, `control-layout`, `composer` y `updates` cubren entrada/salida del selector, dos orígenes con el mismo bundle, todos los transportes al mismo destino, limpieza, doble toque, fallo de disco, respuesta posterior al desmontaje y protección de contenido. Logs en `outputs/p02`. La negociación nuevo/viejo de capacidades continúa en P02-03.

El bundle iOS/Hermes se exportó en `outputs/p02/ios-export`, archivo `entry-9d148dad55767cec5345a9748138eff4.hbc`. Comprueba resolución de módulos; todavía no es un binario nativo ni acredita instalación física. La exportación Android tiene su log separado.

## Migración y rollback

La app anterior tenía una dirección en el código y no un registro persistido. La primera apertura del candidato pide elegir un equipo; no incorpora una dirección personal como valor predeterminado. El esquema v1 admite lectura del archivo JSON legado si existe y escribe revisiones nuevas en dos slots propios. Rechaza cambios sobre una revisión obsoleta y conserva documentos desconocidos. El journal usa un singleton en el runtime JS, sin prometer exclusión entre procesos distintos.

Rollback de código a `12aa1d7`: el cliente anterior conserva su ruta original y no borra los registros v1. Una actualización posterior vuelve a leerlos. Este mecanismo no migra ni elimina permisos, certificados o emparejamientos del servidor.

## Aceptación pendiente

La aceptación requiere un build Expo nativo compatible con la versión instalada, arranque, persistencia tras reinicio, conexión al origen elegido, cambio de equipo y recuperación cuando el archivo no se puede leer o escribir. La aceptación principal sigue siendo Ubuntu+iPhone. Se pueden coordinar pruebas con un Mac de un amigo y un Android de otro amigo, pero todavía no están verificadas sus toolchains, firma, permisos ni disponibilidad efectiva. Esas pruebas no se consideran evidencia hasta ejecutarse.

QR, códigos de emparejamiento, NAT/TURN y distribución pertenecen a P07/P11 y quedan fuera de este bloque.
